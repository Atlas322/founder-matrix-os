# spawn-preflight — сешн үүсгэх / хаахын өмнөх шалгалт

> **itge.e-ийн хувийн skill.** fm v0.3-аас plugin-оос гарсан: Project agent нь төсөл бүрт нэг тогтмол сешн, task-уудыг тэр сешн дотор хийдэг тул энгийн гишүүнд олон сешн spawn хийх хэрэггүй. Суулгах: энэ файлыг `~/.claude/skills/spawn-preflight/SKILL.md` болгон хуул. Скрипт: repo-ийн `extras/personal/spawn_preflight.py` (fm plugin-ий `fm_project.py`, `fm_role.py`-г ашиглана).

Эзэн дүр: **Project** (төслийн сешн). GTD, Area, Resource дүрүүд ч өөрийн сешнээ үүсгэхдээ ашиглана.

## Яагаад

Сешнийг төслийн **агшин зургаар** үүсгэвэл нэг цагийн дотор хуучирч болно: хэрэглэгч төслийг `on-hold` болгосны дараа шинэ сешн паркалагдсан ажил руу заасан өнчин болно. Дүрийн prompt-д «шалга» гэж бичих нь урт сешнд бүдгэрдэг. Тиймээс шалгалт **үйлдлийн мөчид ажилладаг скриптэд** амьдарна.

Vault: `<vault>`

## Алхам 1 — Скрипт (алгасах эрхгүй)

```bash
python3 "$HOME/Documents/CodeBase/founder-matrix-os/extras/personal/spawn_preflight.py" "<vault>"
```

(Windows: `python` / `py -3`.) Гаралт: төсөл бүрийн `status` · сүүлд хөдөлсөн · нээлттэй таск · хүрээний гэрээ (n/4) · бүртгэлтэй сешнүүд (дүр · төхөөрөмж) · дүрийн хамралт · (vault git-тэй бол) ажлын мод, worktree.

## Алхам 2 — Амьд сешнүүд

Claude Desktop дээр: `ToolSearch: select:mcp__ccd_session_mgmt__list_sessions` → `list_sessions`. `group`, `cwd`, `isArchived`, `isRunning`-ийг хар. Хэрэгсэл байхгүй бол хэрэглэгчээс нээлттэй сешнүүдийн жагсаалтыг асуу.

⚠️ Олон сешнд **нэгэн зэрэг** хандахын өмнө (хурал, олон мессеж) оролцогч бүрийн `isArchived`/`isRunning`-ийг **тэр агшинд** дахин шалга. Архивлагдсан сешн мессеж хүлээж авахгүй, хариу хэзээ ч ирэхгүй.

📌 **Архивлагдсан ≠ устгагдсан.** Transcript нь `~/.claude/projects/<slug>/*.jsonl` дор хэвээр — асууж чадахгүй ч уншиж чадна.

## Алхам 3 — Тулга

| Олдвор | Утга |
|---|---|
| `[*]` төсөл, сешнгүй | **ҮҮСГЭХ** нэр дэвшигч |
| Сешн байгаа, төсөл нь `[ ]` (on-hold / completed / cancelled) | **ХААХ / архивлах** нэр дэвшигч |
| Нэг дүр нэг төхөөрөмж дээр 2 сешнтэй («давхар») | Нэгийг хаах нэр дэвшигч |
| Registry-д `— дүргүй` сешн | `/fm:role`-оор холбох эсвэл хаах |
| Сешний `cwd` дотор `.claude/worktrees/` (vault сешн) | 🔴 Obsidian харахгүй — доорх §Worktree |
| `гэрээ 0/4 🔴` | Доорх Алхам 3в |

### 3а — Өөрийн үүсгээгүй сешн олдвол ЭХЛЭЭД АСУУ

Хэрэглэгч өөрөө сешн нээж ажил хийлгэсэн байж болно. Brief бичихээс **өмнө**:
1. Тэр сешн рүү мессеж: «юу хийчихсэн бэ · одоо юу дээр байна · юу нь хуучирсан бэ».
2. Хариу ирэх хүртэл brief бичихгүй.
3. Brief-д зөвхөн **үнэхээр үлдсэн** ажлыг бич. Хийгдсэн ажлыг дахин даалгах нь давхар ажил үүсгэнэ.

📌 Дискнээс шалга, санах ойноос бичихгүй — сешний хувьд «диск» нь тэр сешн өөрөө.

### 3б — Brief-д тайлагнах үүргийг заавал бич

Доорх блокийг spawn prompt-д **үгчлэн** оруул:

```
## Тайлагнах үүрэг (заавал)
- Ээлж бүрийн төгсгөлд `_system/logs/<өнөөдөр>.md`-д **append** хий
  (огноог `date +%F` эсвэл Python-оор уншина, санах ойноос биш)
- Дараах тохиолдолд Project дүрд task үүсгэж мэдэгдэ (/fm:task, owner `project`):
  · хэрэглэгч шинэ даалгавар өгсөн
  · төслийн `status` · `goal` · хүрээ өөрчлөгдсөн
  · өөр сешнтэй эзэмшил давхцсан
  · brief-ийн аль нэг хэсэг хуучирсан
- Лог бол анхдагч суваг; task бол нэмэлт, орлуулагч биш
```

### 3в — Хүрээний гэрээ байгаа эсэх

Сешн байгаа атлаа «юу хийвэл дуусахыг» хэн ч бичээгүй бол сешн зогсохгүй — хэрэггүй ажил үргэлжилнэ. Амьд сешнтэй төсөл бүрд:

```
goal:        устсан/өөрчлөгдсөн зүйлийг заасаар байна уу?
due: эсвэл   «юу болвол дууссан» хаа нэгтээ бичигдсэн үү? (_BRAIN.md)
milestones:  огноогүй мөр хэдэн сар зогсож байна вэ?
anti-goal:   юу нь энэ төсөлд ХАМААРАХГҮЙ вэ?
```

⛔ Дөрвүүлээ хоосон бол шинэ ажил даалгахаас **өмнө** хэрэглэгчид хүрээний асуулт тавь. `goal`-ыг өөрөө бүү дахин бич — илрүүлж, асуулт болгон тавь.

## Алхам 4 — Зөвшөөрөл

Зөрүүг **үсэгтэй сонголтоор (A/B/C)**, тус бүрд нэг мөр trade-off-оор үзүүл. **Зөвшөөрөлгүйгээр сешн бүү үүсгэ, бүү хаа.** `active`/`planning` биш төсөлд сешн үүсгэхгүй — хэрэглэгч тодорхой «тийм» гэвэл л.

### 4а — Шинэ төсөл бол

| Шалга | Яагаад |
|---|---|
| Гол нэр үгийг **кириллээр батлуул** | Латин галиг хоёр утгатай — буруу нэрээр хавтас нээгдвэл сешний cwd болж солиход хэцүү |
| `_BRAIN.md`-г хамт үүсгэ (`/fm:project new`) | Brain-гүй төсөл дүрэмгүй эхэлнэ |
| Бүтэн зам < 60 тэмдэгт | Урт зам дээр синк/устгалын асуудал гарч байсан. Урт бол богино нэр + `aliases:` |
| Хэрэглэгч хавтас/файл тавьсан бол эхлээд унш | Brief-ийг агуулгаар нь бич, нэрээр нь биш |
| Хүлээн авагчийг **session id**-аар заа (registry) | Нэр хоёр сешнд таарч болно |

## Алхам 5 — Үүсгэх

Claude Desktop: `mcp__ccd_session__spawn_task` (байхгүй бол prompt-ийг хэрэглэгчид өгч өөрөө нээлгэ). Prompt **бие даасан** байх ёстой — шинэ сешн энэ яриаг харахгүй. Заавал 7 хэсэг:

1. **Дүр** — «Чи бол <Төсөл>-ийн сешн. Дүр: <slug>. <хэн> <огноо>-нд үүсгэв.» + эхний мөрөнд `/fm:role <slug>` ажиллуулах заавар.
2. **Эхлээд унш** — `_BRAIN.md`, төслийн нот, дүрийн тэмдэглэл.
3. **Хүрээ** — юу хамаарах, юу хамаарахгүй (эцэг/дэд төслийн хил).
4. **Нээлттэй таск** — нэрээр, статустай. Тоо биш, жагсаалт.
5. **Эхний алхам** — нэг тодорхой үйлдэл + «хэрэглэгчид A/B/C-ээр санал болго».
6. **Зэрэгцээ сешний дүрэм** — доорх блок үгчлэн.
7. **Схемийн дүрэм** — доорх блок үгчлэн.

```
## Зэрэгцээ сешний дүрэм (заавал)
Хэрэглэгч олон сешн зэрэг ажиллуулдаг, бүгд нэг vault дээр (Drive синк):
- `00-GTD/Daily/*`, `_system/logs/*`, `04-Areas/people/*` — олон сешн бичдэг.
  Дарж бичихгүй, **зөвхөн append**, өөрийн тэмдэглэсэн хэсэгт.
- Зөвхөн энэ төслийн authored нот дээр эзэмшил зарла.
- Хоёр машин нэг файлыг зэрэг бичвэл Drive `(1)` давхардал үүсгэнэ — нэг файлыг нэг л газар засна.
- Код репод git ашиглавал `git add -- <тодорхой зам>`; `git add -A` ХЭЗЭЭ Ч ҮГҮЙ.
```

```
## Схемийн дүрэм (заавал)
Таск, төсөл, уулзалтын нот үүсгэх бүрд `context:` талбар тавь:
    context: home | work
`area` талбараас: Business · Product · System → work; Personal · Self-improve → home.
Таск эцэг төслийнхөө `context`-ийг өвлөнө.
Яагаад: Projects/Tasks харагдацын 🏠 Home / 💼 Work шүүлтүүр энэ талбараас гарна.
Талбаргүй нот хоёуланд нь харагдахгүй — чимээгүй алга болно.
```

Үүсгэсний дараа: шинэ сешнийг `/fm:role`-оор дүрд холбосон эсэхийг preflight-ийн «БҮРТГЭЛТЭЙ СЕШНҮҮД»-ээс шалга.

## Worktree — vault сешнд ХОРИОТОЙ

| Сешний `cwd` | Worktree |
|---|---|
| Vault дотор | ⛔ Хориотой — Obsidian зөвхөн үндсэн хавтсыг индексжүүлдэг; салаа хоцорч хуучирсан vault уншина; append merge conflict болно |
| Vault-аас гадуур код репо | ✅ Зөвшөөрнө |

`spawn_task`-ийн chip өгөгдмөлөөр worktree нээж болно — хэрэглэгч товшихоос **өмнө** «worktree унтраа» гэж бичгээр сануул. Brief-д «worktree бүү үүсгэ» гэж **болзолгүй** бичихгүй — cwd-ээр ялга.

Худал worktree илэрвэл: `git -C <worktree> log --oneline main..HEAD` ба `git -C <worktree> status --porcelain`-ээр алдагдах зүйл байгаа эсэхийг эхлээд шалга. Commit байвал хэрэглэгчид сонголт үзүүл — сохроор merge хийхгүй.

## «MCP ажиллахгүй байна» ≠ архивлах шалтгаан

MCP сервер сешн **эхлэх/дахин холбогдох** агшинд ачаалагддаг. Архивлахаас өмнө:
1. Тохиргоонд (`~/.claude.json` / plugin) тэр сервер байна уу?
2. Тухайн төсөлд идэвхгүй болгосон жагсаалт байна уу?
3. Сешний transcript-д `mcp__<нэр>__` хэзээ нэгэн цагт гарсан уу?

«байна · үгүй · тийм» бол асуудал өөрөө шийдэгдэнэ. Архивлах нь контексттэй сешнийг алддаг тул хамгийн сүүлийн арга.

## Хаах үед

Төсөл хаагдаж байвал эхлээд `/fm:project`-ийн **хаах шалгах жагсаалт**. Сешн өөрөө:

| # | Алхам |
|---|---|
| 1 | Сешний ажил vault/репод хадгалагдсан эсэхийг шалга (лог, devlog, commit) |
| 2 | Нээлттэй асуулт, дуусаагүй ажлыг **бүтэн текстээр** handoff тэмдэглэлд эсвэл task болгон үлдээ |
| 3 | Хүлээн авагчийг **session id**-аар тогтоо — нэр 2+ сешнд таарвал зогс |
| 4 | Логт «илгээв» ба «хүлээн авав»-ыг **тусдаа мөр**-өөр бич. «мэдэгдэв» гэж бүү бич |
| 5 | Хүлээн авагчийн ack-ийг хүлээ. ⚠️ ack бол хаах **боломж**, зөвшөөрөл биш — зөвшөөрөл хэрэглэгчээс |
| 6 | Registry-аас тэр сешний мөрийг цэвэрлэх нь Area дүрийн ажил — task үүсгэж дамжуул |
